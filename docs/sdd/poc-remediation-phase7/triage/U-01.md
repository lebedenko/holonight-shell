| I-07 | Logger console-output path is unsynchronized while the file-write path is explicitly mutex-protected | Refuted | — | Not in manifest — `Logger.cpp` unchanged. Re-read at current `:114-135` (unshifted) confirms the console-print block is not guarded by `ctx.log_mutex` (which only wraps the file-write block at `:88-95`), and confirms multiple services do log from `QtConcurrent` worker threads elsewhere in the tree, matching the original's premise. However: `messageHandler()`'s console output goes through `std::println(stdout/stderr, ...)` (`:131,133`), which on this platform wraps the C library's buffered stdio `FILE*` write path. POSIX mandates that stdio operations on a given stream (via the non-`_unlocked` entry points, which is what `std::println`/`fprintf`-family functions use) are individually atomic with respect to other threads' stdio calls on the same stream — each call internally acquires and releases the stream's lock. This means concurrent `messageHandler()` invocations from different threads cannot tear or byte-interleave a single log line's output; only the *ordering* of complete, distinct log lines across threads is non-deterministic, which is inherent to any multi-producer logger and isn't fixable by adding a second application-level mutex around calls that are already individually atomic one layer down. The original finding's claim that console output "relies on unstated libc stream-locking rather than an explicit guarantee" is the disproof itself once traced: that guarantee is not unstated, it's POSIX-standard behavior for `stdio` streams, so there is no missing synchronization here — file writes need the explicit `ctx.log_mutex` because they interleave across the *custom* `QFile`/`QTextStream` object (which has no built-in cross-thread guarantee of its own), while console writes go through the C stdlib's own already-synchronized path. |
